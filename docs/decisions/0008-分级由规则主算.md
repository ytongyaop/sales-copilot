# ADR-0008：客户分级由规则主算，模型只抽取与解释

- **状态**：已接受
- **日期**：2026-11-18
- **背景**：分级（A / B / C）决定「今天先打给谁」，也决定销售看到的第一屏顺序，所以它必须**可解释、可复现、可对账**。v2 初稿把这活儿交给分拣模型：模型一次吐出 `grading.value` + `reason` + `basis`，规则只在模型输出不合法时兜底。问题有三个：① 同一段原文换一次调用就可能从 B 变 A，销售无法理解、复盘也无法归因；② 没有「缺信息」这个状态——模型不知道就说 B，把「还没问」伪装成「已经判了」；③ 模型的分级与详情页的分级各走一套逻辑（详情页没有分级，分拣单上的档位无人复核），同一家客户在不同页面可能显示不同结论。仲裁结论因此定为 C 方案：**分档永远由规则产出，模型不参与打分**。
- **选项**：
  - A：**模型直接给档**（初稿做法）——省事，但不可复现、不可审计；改判没有基线，"为什么是 B" 只能读模型的小作文。
  - B：**纯人工定档**——最准，但每家客户每次变化都要人重判，等于把判断负担全还给销售，且没有一致性。
  - C：**规则四维打分 + 上下界 + 人工改判留痕**（本次所选）——模型只负责从原文里抽取事实（金额 / 约定时间 / 决策者 / 匹配点），打分与分档由 `domain/grading.py` 按模板权重算；信息不全时用上下界表达「可能是什么档」，跨档就是 `needs_info`。代价是四维口径与权重需要维护，且必须先有事实才能出档。
- **决策**：选 **C**。具体口径：
  - ① **模型只抽取**：模型负责把原文变成事实（带 `source_span`），不再输出档位；分拣单里模型那份 `grading` 只留在 `suggestion_json` 供审计，不参与分档。
  - ② **四维打分**：`amount`（≥50 万 1.0 / ≥10 万 0.7 / >0 0.4）、`urgency`（≤7 天 1.0 / ≤30 天 0.6 / 更远 0.3）、`clarity`（决策者 + 决策流程齐全 1.0 / 只一项 0.5）、`fit`（我方匹配点 1.0 / 只有核心需求 0.5）；解析不出来就算**未知**，不当 0 分。
  - ③ **未知用上下界**：`low` = 已知维度按实得分，`high` = `low` + 未知维度的满权重。`high < b_min` → C；`low ≥ a_min` 且四维齐全 → A；`low ≥ b_min` 且 `high < a_min` → B；其余（跨档）→ `needs_info`。
  - ④ **A 档要求四维齐全**：四缺一的「高分」不算 A——缺的那一维可能把结论推翻，先把话问全再谈优先级。
  - ⑤ **权重与阈值只来自模板**：`grading.weights` / `grading.bands` / `grading.default_mode` 写在 `templates/*.yaml`，模板校验保证四维齐全、和为 1（±0.001）、`a_min > b_min`；代码里不写死数字。
  - ⑥ **双模式 + 留痕三列**：`propose` 只写建议行（`ai_value` 有值、`human_value` 为空），等人工 `decide`；`auto` 在建议之后立刻再写一行采纳（`ai_value == human_value`）。`grading_history` 只追加，改判必须写理由（≥2 字），`ai_value` / `human_value` / `reason` 三列永远并存。
  - ⑦ **一套口径两处用**：分拣单的分级与 `POST /leads/{id}/grading/propose` 调的是同一个 `grade_from_facts`，只是分拣单把要素临时映射成事实（不落库）。
- **后果**：
  - 变好：同一批事实 + 同一天永远同一档，测试与服务都能对账；「为什么是 A」是一句可核算的话（四维得分 + 加权 + 门槛）；缺信息时给 `needs_info` 而不是硬判，销售知道该补哪一句；改判有留痕，能回答「谁在什么时候把 A 改成 C、为什么」；模板换行业只改权重与阈值，代码不动。
  - 变差：必须先有事实才能出档，事实层空着的客户一律 `needs_info`，看起来「系统什么都没说」；四维口径固定，遇到模板覆盖不到的判断依据（比如竞争格局）无法进模型；分拣单上会出现 `needs_info`，前端要能展示第四种状态。
  - 要还的债 / 代价：权重与阈值目前是拍的默认值（0.3 / 0.3 / 0.2 / 0.2、0.75 / 0.45），需要用真实成交样本回测校准（与 ADR-0007 的阈值校准同一套路子，尚未排期）；`amount` 的中文数字解析只覆盖常见写法，生僻写法会落到「金额无法解析」。
- **确认方式**：
  - 测试：`tests/test_grading_domain.py`（四维齐全才可能 A、缺一维不得为 A、上下界同档出 B/C、跨档出 `needs_info`、金额四种写法、紧迫度三档）、`tests/test_grading_service.py`（提议落一行、改档必填理由、auto 两行、历史倒序只追加）、`tests/test_grading_api.py`（200/201/422/404）、`tests/test_templates.py`（权重和 ≠ 1、`a_min ≤ b_min`、缺段都报错）、`tests/test_sorting_service.py`（分拣单的档位与 `grade_from_facts` 逐字相同）。
  - 留痕：`GET /leads/{id}/grading/history` 能查到「AI 值 / 人工值 / 理由」三列齐全的流水，改判后行数递增、旧行不变。
  - 一次人工走查：干净库建客户 → 补金额 / 约定时间 / 决策者 / 匹配点 → `POST propose` 得 A → `decide` 改 C 并写理由 → `GET history` 两行；再 `POST propose?mode=auto` 看到「建议 + 采纳」两行。
