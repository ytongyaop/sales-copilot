# ADR-0003：业务数据与知识库分离

- **状态**：已接受
- **日期**：2026-11-13
- **背景**：系统里有两类完全不同的数据访问模式。线索、跟进、阶段历史、归属事件、AI 调用记录要事务性与强一致，还要能回答"这个数字为什么变了"；产品/课程资料要的是相似度检索。放同一个库里，要么业务查询不可靠，要么检索质量差。
- **选项**：
  - A：SQLite 存业务真源 + Chroma 只存知识向量，运行时只读
  - B：向量库兼做业务库 —— 向量库没有业务查询需要的事务语义，按 id 查慢且不可靠
  - C：全放 SQLite，自己做向量相似度 —— 检索质量差，且要额外写一套相似度实现
- **决策**：选 A。SQLite 是业务唯一真源；Chroma 只存产品/课程资料向量，**只由脚本写入**，请求路径一律只读。
- **后果**：
  - 变好：两类数据各用对的存储；知识库可随时整库重建而不影响业务数据；资料更新不产生业务事务。
  - 变差：双存储，必须靠规则守住一致性 —— ① 索引只由脚本写、运行时只读；② 索引清单记录 embedding 模型名，换模型必须重建索引，否则查询向量与旧向量不在同一空间，检索会静默变差而没人发现。
  - 要还的债：资料与索引不同步时没有增量修复，只能整库重建；v1 不做增量索引。
- **确认方式**：改一份资料但不跑索引脚本，检索仍返回旧结果（证明运行时只读）；跑重建脚本后返回新结果；索引清单里的 embedding 模型名与当前配置一致。
